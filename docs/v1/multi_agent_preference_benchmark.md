# Multi-Agent Preference Memory Benchmark 设计说明

## 1. 文档目的

本文定义 Agent Memory Benchmark 的“多 Agent 用户偏好记忆”评测轨道（Preference Track v0）。

现有 T4（split intake）和 T2（compound update）主要测试精确事实的保留与更新，例如设备型号、日期、配置和状态变化。它们能够发现记忆系统在事实完整性上的风险，但不能回答另一类同样重要的产品问题：

> 当不同 Agent 在不同时间、不同任务中分别获得用户偏好后，一个没有见过原始对话的新 Agent，能否通过共享记忆理解并正确应用用户当前有效的偏好？

Preference Track v0 不以证明某个系统“更好”为目标，也不预设 mem0 应该获胜。它的目标是补齐场景覆盖，比较不同记忆架构在跨 Agent 偏好共享、合并、更新和边界控制上的表现，并形成“什么系统适合什么记忆工作”的能力地图。

本轨道是第一版 pilot。它首先验证任务设计和系统区分度，不作为最终行业排名。

---

## 2. 为什么要增加用户偏好评测

### 2.1 现有评测偏重高保真事实

T4 和 T2 更接近“事实档案”任务：用户明确说过的具体信息应被完整保留，更新后的新值应生效，未被更新的事实不应受损。这类任务天然重视原文保留和精确召回。

但实际 Agent memory 还常被用于：

- 记住用户喜欢怎样的回答方式；
- 从多个 session 中归纳稳定偏好；
- 合并不同 Agent 分别观察到的偏好碎片；
- 在用户偏好改变后使用新偏好；
- 区分长期偏好、特定场景偏好和一次性要求；
- 用更短的记忆支持跨 session 个性化。

这些工作可能更适合具有语义抽取、归纳和更新能力的记忆系统。只有将它们纳入评测，才能避免把一个“精确事实测试”错误扩大成“所有 memory 能力的总排名”。

### 2.2 Multi-agent 的真实要求

本轨道不能退化成“Agent A 得到偏好，Agent A 自己以后再使用”。真正的 multi-agent 偏好记忆至少需要满足：

1. 不同 writer Agent 只看到各自的局部用户对话；
2. 没有任何单个 writer Agent 天然拥有全部偏好历史；
3. 最终 decision Agent 没有看过 writer Agent 的原始对话；
4. decision Agent 只能通过共享 memory 获得历史偏好；
5. 多个 Agent 写入的偏好可能互补、更新、具有不同作用域，或只在一次任务中有效。

因此，本轨道测试的是共享 memory 是否能在多个 Agent 之间传递并维护正确的用户偏好状态，而不只是测试一个带有不同 `agent_id` 标签的单 Agent 流程。

## 3. 评测对象和不测内容

### 3.1 正式比较的三个系统

| 系统 | 写入与存储方式 | 读取方式 | 在本轨道中的代表意义 |
|---|---|---|---|
| `naive_markdown` | 原样追加所有写入 | 返回全部历史 | 完整原文基线 |
| `AMH` | 原文写入 Markdown/文件式共享记忆 | 关键词检索 | Multi-agent-native、可追溯原文记忆 |
| `mem0` | LLM 抽取、整理和更新记忆 | 向量检索 | 语义抽取与归纳型记忆 |

### 3.2 不测 `pure_vector`

Preference Track v0 每个 case 只有少量写入。当前 `pure_vector` 返回 top-8，在这种规模下往往会返回全部或绝大部分内容，与 `naive_markdown` 的信息增量有限。

`pure_vector` 应在未来的长历史和大量噪声任务中重新加入。届时，向量检索能否从 100～1000 条历史中找回相关偏好才是关键问题。

### 3.3 `no_memory` 不进入正式排行榜

主流长期记忆 benchmark 通常比较完整上下文、RAG、不同记忆系统或 oracle retrieval，而不是让空记忆方案完整跑过所有题目。因此，本轨道不将 `no_memory` 作为正式参赛系统。

无历史输入只用于 case 生成后的数据质量检查：判断候选项是否存在不依赖用户偏好也能明显猜中的默认最优解。该检查不计入正式系统结果。

### 3.4 第一版明确不测的内容

- 不测试 Agent 自行推断出的隐含人格或偏好；
- 不测试真实用户行为与口头偏好不一致的情况；
- 不测试隐私、权限、跨用户泄漏；
- 不测试 100～1000 条以上的长期历史扩展性；
- 不测试不同 LLM vendor 的 writer/reader 差异；
- 不将结果扩大为三个系统在所有 memory 场景中的总体排名。

Preference Track v0 只使用用户明确表达的长期偏好、场景偏好、偏好更新和一次性要求，以减少 Agent 推断能力对 memory 评测的干扰。

---

## 4. 核心研究问题

Preference Track v0 回答以下产品问题：

1. **跨 Agent 共享与合并**：Agent A 和 Agent B 分别得到的偏好，后来的 Agent D 能否综合使用？
2. **偏好更新**：用户明确改变偏好后，Agent D 是否使用新偏好并停止使用旧偏好？
3. **偏好边界**：系统能否区分长期偏好、特定场景偏好和一次性要求？
4. **综合应用**：上述能力同时出现时，Agent D 最终能否做出符合用户当前有效偏好的决定？
5. **错误传播控制**：系统是否会把过期偏好、错误作用域偏好或临时要求传播给新的 Agent？
6. **效率代价**：达到相同正确率时，不同系统需要提供多少 context，并产生多少调用、延迟和成本？

---

## 5. 为什么同时需要单项和综合测试

两类测试回答不同问题：

- **单项测试用于诊断**：系统失败时，判断它主要不会共享合并、不会更新，还是不会处理偏好边界；
- **综合测试用于验证真实结果**：多个 Agent、多类偏好、更新和临时要求一起出现时，最终用户结果是否正确。

只测单项，可能得到“每项基础能力都不错，但组合起来不好用”的假象；只测综合，则只能知道系统整体分数低，却不知道原因和改进方向。

因此采用类似“组件测试 + 端到端用户流程测试”的两层结构，但第一版只保留三类核心单项和一种综合流程，避免过度复杂。

---

## 6. Case 规模与组成

正式 pilot 共 60 个 case：

| 测试层 | 类型 | 数量 | 主要目的 |
|---|---|---:|---|
| 单项 | 跨 Agent 共享与合并 | 10 | 定位共享、召回和信息合并问题 |
| 单项 | 偏好更新 | 10 | 定位新旧偏好处理问题 |
| 单项 | 偏好边界 | 10 | 定位作用域和过度记忆问题 |
| 综合 | 15 组反事实双胞胎 | 30 | 验证完整 multi-agent 用户流程 |
| **合计** |  | **60** |  |

正式运行前，先跑 12 个 smoke case：

- 跨 Agent 共享与合并：2 个；
- 偏好更新：2 个；
- 偏好边界：2 个；
- 综合反事实双胞胎：3 组，共 6 个。

Smoke 的目的不是发布结论，而是验证：

- 输出格式是否稳定；
- 每个 case 是否存在唯一正确答案；
- 不看历史时是否存在明显默认答案；
- 反事实偏好变化是否确实应当改变选择；
- 三个系统之间是否有初步区分度；
- 系统 reset、错误记录和完整 context 保存是否可靠。

## 7. 三类单项测试

### 7.1 跨 Agent 共享与合并：10 个

#### 流程

1. Agent A 只看到用户偏好的一部分，并将用户原话写入共享 memory；
2. Agent B 只看到另一部分互补偏好，并将用户原话写入同一 memory；
3. Agent D 没有见过 A、B 的原始对话；
4. Agent D 根据共享 memory，从三个有真实 trade-off 的候选方案中选择一个。

#### 示例

Agent A：

> 用户旅行时不喜欢吵闹、人多的地方。

Agent B：

> 用户喜欢有本地特色的小酒店，不喜欢大型连锁。

Agent D 当前任务：

> 为用户选择一家京都酒店。

候选：

- A：市中心大型连锁，交通方便但环境热闹；
- B：安静的本地精品酒店，距离稍远；
- C：机场商务酒店，网络稳定。

正确选项为 B。该 case 重点测试 A、B 的偏好是否能跨 Agent 共享，并被 D 综合使用。

### 7.2 偏好更新：10 个

#### 流程

1. Agent A 得到用户较早的偏好；
2. Agent B 较晚得到用户明确的新偏好，并包含清楚的替代信号；
3. Agent D 只能通过共享 memory 判断当前偏好；
4. Agent D 在能分别满足新旧偏好的候选之间做选择。

#### 示例

Agent A：

> 用户买设备时价格优先，够用就行。

Agent B：

> 最近设备故障影响了工作。以后稳定性优先，贵一点没关系，不再把价格放在第一位。

候选：

- A：便宜 30%，但故障率较高；
- B：贵 30%，但稳定性明显更好。

正确选项为 B。该 case 同时检查新偏好是否生效、旧偏好是否停止被当作当前偏好，以及是否出现新旧混用。

### 7.3 偏好边界：10 个

该类型合并三个相关问题：

- 长期偏好与特定场景偏好的边界；
- 一次性任务要求是否被错误永久化；
- 其他场景的偏好是否污染当前任务。

#### 流程

1. Agent A 得到长期偏好或某个明确场景的偏好；
2. Agent B 得到另一个场景偏好或一次性要求；
3. Agent D 在一个新任务中做决定；
4. D 应使用当前场景有效的偏好，并忽略错误作用域或已经结束的一次性要求。

#### 示例

Agent A：

> 用户私人度假时喜欢安静、慢节奏的小酒店。

Agent B：

> 这次商务出差只有一天，请优先选择离会场近的连锁酒店。

Agent D 当前任务：

> 这是一次新的私人度假，请选择酒店。

D 应使用“安静、慢节奏、小酒店”，不能把上一次出差的“离会场近、连锁酒店”推广为永久全局偏好。

---

## 8. 综合测试：15 组反事实双胞胎，共 30 个 case

### 8.1 统一流程

每个综合 case 使用一条完整 multi-agent 用户旅程：

1. Agent A 获得一个长期或稳定偏好；
2. Agent B 获得互补偏好或偏好更新；
3. Agent C 获得另一个场景偏好或一次性要求；
4. Agent D 没有看过 A、B、C 的原始对话；
5. Agent D 根据当前任务查询共享 memory；
6. Agent D 从三个候选方案中做选择，并输出其使用的偏好代码。

每个综合 case 同时覆盖两到三种能力，但不再拆分多种综合类别，以保持第一版设计可解释、可执行。

### 8.2 反事实双胞胎

每个基础情境生成两个版本：

- 当前任务完全相同；
- 候选方案及其排列保持配对可比；
- 只有历史中的用户偏好相反；
- 两个版本的正确选项不同。

示例：同一组三家酒店、同一个京都私人度假任务。

- 用户甲偏好安静、本地特色、小型酒店，正确选择 B；
- 用户乙偏好市中心交通、完整设施和品牌稳定性，正确选择 A。

如果系统在两个版本中总选相同酒店，它可能遵循的是 reader LLM 的默认倾向，而不是真正使用了共享 memory。只有一对中的两个版本都正确，才算该反事实组成功。

反事实双胞胎在统计分析中按“组”处理，不能假装是 30 个完全独立样本。

---

## 9. 每个 Case 的标准运行流程

```text
1. 为该 case 创建全新、独立的 memory store
        ↓
2. Agent A 只获得对话 A，并把用户原话写入共享 memory
        ↓
3. Agent B 只获得对话 B，并把用户原话写入共享 memory
        ↓
4. 综合 case 中，Agent C 写入场景偏好或一次性要求
        ↓
5. Agent D 只获得当前任务和候选方案，不获得历史原文
        ↓
6. 使用固定 query 查询共享 memory
        ↓
7. 完整保存 memory 返回的 retrieved context
        ↓
8. Agent D 仅根据 retrieved context、当前任务和候选进行选择
        ↓
9. Agent D 输出固定 JSON：choice + applied_preference_codes
        ↓
10. 程序将输出与隐藏 ground truth 比较并记录各项指标
```

### 9.1 Writer Agent 的行为约束

第一版不让 writer Agent 自己总结或决定“什么值得写”。Runner 将各 Agent 局部对话中的用户原话直接交给被测 memory system。

原因是本轨道要隔离测试共享 memory 层。如果同时让 Agent 自己决定写什么，将混入 Agent prompt、写入策略和模型能力差异，导致系统分数难以解释。

### 9.2 Decision Agent 的信息边界

Agent D 只能看到：

- 当前任务；
- 三个候选及其结构化属性；
- 被测 memory system 针对当前 query 返回的 context。

Agent D 不能看到：

- A、B、C 的原始对话；
- ground truth；
- 哪些偏好代码被标记为有效或无效；
- 反事实双胞胎的另一半。

三个系统必须使用同一个 reader LLM、同一个 system prompt、同样的温度和输出格式。

## 10. Ground Truth 设计

### 10.1 Ground truth 不是只有一个正确选项

每个 case 的隐藏 ground truth 至少包含：

- 各 Agent 分别观察到的偏好事件；
- 偏好来源、时间和作用域；
- 当前任务中有效的偏好；
- 已被更新替代的旧偏好；
- 属于其他场景的偏好；
- 已结束的一次性要求；
- 候选方案的结构化属性；
- 唯一正确选项；
- 正确决定应使用的理由代码；
- 不应使用的理由代码。

示例：

```json
{
  "current_context": {
    "domain": "travel",
    "trip_type": "leisure"
  },
  "active_preferences": [
    "quiet",
    "boutique",
    "local_character"
  ],
  "wrong_scope_preferences": [
    "venue_proximity",
    "business_wifi_priority"
  ],
  "expired_preferences": [
    "airport_proximity"
  ],
  "superseded_preferences": [],
  "expected_choice": "B",
  "required_reason_codes": [
    "quiet",
    "boutique"
  ],
  "forbidden_reason_codes": [
    "venue_proximity",
    "airport_proximity"
  ]
}
```

### 10.2 Ground truth 状态规则

所有 case 使用统一规则生成当前有效偏好状态：

1. **当前明确要求优先于历史偏好**；
2. **用户明确表达优先于 Agent 推断**；第一版不把 Agent 推断作为有效 ground truth；
3. **同一作用域中，较新的明确更新覆盖旧偏好**；
4. **更具体的作用域只在对应场景中生效**，不能无依据推广为全局偏好；
5. **一次性要求只对绑定任务有效**，任务结束后失效；
6. **互不冲突且作用域兼容的稳定偏好可以合并**；
7. **当证据不足或规则不能给出唯一有效状态时，该 case 不进入正式数据集**。

### 10.3 正确选项的生成

每个候选方案都有结构化属性，例如：

```json
[
  {
    "id": "A",
    "attributes": {
      "quiet": false,
      "boutique": false,
      "local_character": false,
      "city_center": true,
      "large_chain": true
    }
  },
  {
    "id": "B",
    "attributes": {
      "quiet": true,
      "boutique": true,
      "local_character": true,
      "city_center": false,
      "large_chain": false
    }
  }
]
```

第一版不使用复杂、可争议的主观权重模型。Case 生成器只保留满足以下条件的题目：

- 当前有效偏好能够明确区分候选；
- 存在唯一正确选项；
- 每个候选都有真实优势和代价，不存在脱离偏好也明显最好的选项；
- 反事实偏好版本会产生不同的唯一正确选项。

如果出现平局、规则冲突或多个合理答案，重新生成或人工剔除该 case。

---

## 11. Decision Agent 输出格式

为了稳定地进行程序评分，Agent D 必须返回固定 JSON：

```json
{
  "choice": "B",
  "applied_preference_codes": [
    "quiet",
    "boutique",
    "local_character"
  ]
}
```

`choice` 是核心产品输出；`applied_preference_codes` 用于诊断是否使用了正确、当前有效的偏好。

偏好理由不能单独证明成功，因为 LLM 可能事后生成看似合理的解释。因此：

- 最终选择是核心评分；
- 理由代码是诊断评分；
- 反事实成对成功是判断 memory 是否真正影响行为的重要控制。

JSON 解析失败应计为系统/回答错误，不得静默排除。可额外保存原始回答用于复核。

---

## 12. 核心指标

### 12.1 决策正确率（Decision Accuracy）

```text
正确选择的 case 数 / 可评分 case 总数
```

衡量最终 Agent 是否做出了符合当前用户偏好的决定，是本轨道的首要产品指标。

### 12.2 有效偏好覆盖率（Active Preference Recall）

```text
正确使用的有效偏好代码数 / ground truth 中要求使用的有效偏好代码数
```

用于判断系统是否只找回或应用了部分偏好。该指标是诊断指标，不能替代决策正确率。

### 12.3 无效偏好使用率（Invalid Preference Rate）

```text
使用的无效偏好代码数 / Agent 使用的全部偏好代码数
```

无效偏好包括：

- 已被新偏好替代的旧偏好；
- 属于其他场景的偏好；
- 已结束的一次性要求；
- 用户从未明确表达的偏好。

当 Agent 未输出任何偏好代码时，应单独记录，不能用分母为零制造“0% 错误偏好”的假性好成绩。

### 12.4 反事实成对成功率（Counterfactual Pair Success）

```text
两个反事实版本都选择正确的组数 / 反事实组总数
```

只有一组中的两个相反偏好版本都答对，才算成功。该指标比单 case 正确率更能证明系统在使用共享 memory，而不是遵循 reader LLM 的默认选择倾向。

### 12.5 严格综合通过率（Strict Composite Pass）

一个 case 同时满足以下条件才算严格通过：

- 选择正确；
- 必要的有效偏好达到预设覆盖要求；
- 未使用错误作用域、过期或被替代偏好；
- 未使用用户从未表达的偏好。

严格通过率适合展示端到端可靠性，但不应替代各分项指标。

### 12.6 运行效率和可靠性

每个系统额外记录：

- retrieved context 字符数和 token 数；
- 写入耗时；
- 检索耗时；
- reader 回答耗时；
- LLM 调用次数；
- 可估算的 token 成本；
- 系统错误数和错误率；
- JSON 解析失败率。

Preference Track 的产品结论应同时考虑质量、成本、延迟和 context 压缩，而不是只比较一个准确率总分。

---

## 13. 必须保存的中间证据

现有 T2/T4 主要保存最终回答和 context 长度，难以区分写入、检索和 reader 使用错误。Preference Track 必须保存：

1. 每个 Agent 的原始局部用户对话；
2. 写入顺序、`agent_id`、时间和场景 metadata；
3. memory system 针对最终 query 返回的完整 context；
4. Agent D 的原始回答；
5. 解析后的 `choice` 和 `applied_preference_codes`；
6. 各项程序评分结果；
7. 系统异常、重试和错误信息；
8. token、延迟和调用统计。

推荐结果记录结构：

```json
{
  "case_id": "PREF-C-0001-A",
  "pair_id": "PREF-C-0001",
  "system": "mem0",
  "writes": [],
  "query": "...",
  "retrieved_context": "...",
  "raw_answer": "...",
  "parsed_answer": {
    "choice": "B",
    "applied_preference_codes": ["quiet", "boutique"]
  },
  "scores": {
    "decision_correct": true,
    "active_preference_recall": 1.0,
    "invalid_preference_rate": 0.0,
    "strict_pass": true
  },
  "usage": {
    "context_tokens": 0,
    "latency_ms": 0,
    "llm_calls": 0
  },
  "error": null
}
```

## 14. Case 质量控制

### 14.1 无历史输入检查

`no_memory` 不参与正式比较，但 case 生成后应进行一次无历史输入检查：

1. 隐藏全部偏好历史；
2. 只给 reader 当前任务和候选项；
3. 检查模型是否能依靠常识或选项质量稳定猜中某个答案；
4. 如果某候选脱离用户偏好也明显更优，重写或删除该 case。

该步骤属于数据集质检，不计入系统排行榜，也不需要针对每个被测系统重复运行。

### 14.2 选项和顺序控制

- 三个候选都必须有真实优点和代价；
- 正确选项不能总是文字更长、属性更多或描述更积极；
- 候选顺序应按 seed 随机化；
- 正确答案在 A/B/C 中应尽量均衡；
- 反事实双胞胎必须相应更新 ground truth，避免位置泄漏。

### 14.3 反事实一致性检查

每组双胞胎必须满足：

- 当前任务相同；
- 候选语义相同；
- 只有历史偏好发生目标性变化；
- 正确选项随偏好变化而改变；
- ground truth 规则能够解释两个版本；
- 不存在仅靠常识就能同时答对两个版本的固定答案。

### 14.4 人工抽查

即使 ground truth 由结构化规则生成，正式运行前仍需人工抽查 smoke 数据和正式数据样本，检查：

- 对话是否自然；
- 偏好是否表达清楚；
- 作用域和时间是否无歧义；
- 候选是否有真实 trade-off；
- 正确答案是否确实唯一；
- 偏好代码是否与自然语言表达一致。

---

## 15. 运行公平性和隔离要求

### 15.1 Case 隔离

每个 case 必须使用全新、独立的 memory store。不能依赖可能静默失败的 `reset()` 后继续运行。

推荐方式：

- 每个 case 新建 adapter 和独立临时存储；或
- reset 后执行空查询验证存储确实为空；
- reset/清理失败直接记录 error，不能静默忽略。

这样可以防止前一个用户或 case 的偏好污染下一个 case。

### 15.2 系统错误处理

- 系统错误应计入可靠性指标；
- 主结果同时报告 `n_total`、`n_scored` 和 `n_errors`；
- 不允许只对成功 case 计算平均分而隐藏系统失败；
- 如需报告“成功运行 case 的质量”，必须与“端到端含错误质量”并列展示。

### 15.3 Reader 控制

三个系统使用相同的：

- reader 模型和模型版本；
- system prompt；
- temperature（建议为 0）；
- query；
- 当前任务；
- 候选属性和输出格式；
- 最大输出长度；
- 重试策略。

如果 API 模型版本不可固定，应保存运行日期和模型返回的版本信息（如可获得）。

## 16. 结果报告方式

不建议把所有指标压缩成一个总分。Preference Track 应展示 capability profile：

| 系统 | 共享与合并 | 偏好更新 | 偏好边界 | 综合决策 | 反事实成对成功 | 无效偏好率 | Context tokens | 错误率 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `naive_markdown` | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| `AMH` | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| `mem0` | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |

报告应重点回答：

- 哪个系统更能跨 Agent 传递并合并偏好；
- 哪个系统更能正确更新旧偏好；
- 哪个系统更少把临时或其他场景偏好传播出去；
- 哪个系统在完整综合流程中更可靠；
- 哪个系统用更少的 context 达到相近结果；
- 各系统的失败模式分别是什么。

不能从本轨道单独得出“某系统全面最好”。最终应与 T4/T2 一起形成架构适配地图：

- 精确事实保真；
- 状态更新；
- 用户偏好共享与应用；
- 未来的长历史检索与成本。

## 17. 建议的业务场景分布

为避免任务只针对一种产品，60 个 case 应覆盖至少三个业务领域，并保持大致均衡：

1. **旅行与推荐**：酒店、行程节奏、交通、餐厅选择；
2. **写作与工作助手**：回答风格、详细程度、决策偏好、文档语气；
3. **购物与客户服务**：价格/稳定性取舍、沟通方式、服务偏好、方案推荐。

不同领域共用同一套偏好状态规则和评分方法。场景内容可以变化，但不能为某个系统定制特殊 prompt 或评分口径。

## 18. 主要风险和限制

### 18.1 合成偏好不等于真实用户内心

Ground truth 测的是系统能否遵循 case 中明确设定的偏好，不代表能够发现真实用户复杂、矛盾或潜意识中的偏好。

### 18.2 选择题弱化了开放任务复杂度

结构化候选和唯一答案提升了可评分性，但与真实开放式推荐或生成任务仍有差距。Pilot 通过后，可增加开放式应用题并进行人工或独立模型复核。

### 18.3 60 个 case 只适合 pilot

60 个 case 足以发现明显差异和验证设计，但不适合支撑过强的行业结论。若 smoke 和 pilot 有区分度，应扩展到 100～300 个 case，并计算置信区间。

### 18.4 Reader 仍是链路变量

最终结果是 memory retrieval 与 reader 使用能力的共同结果。保存完整 retrieved context 后，可以将失败拆成：

- memory 没有返回正确偏好；
- context 中有偏好，但 reader 没正确识别；
- reader 识别了偏好，但最终决策错误。

### 18.5 少量历史仍可能有利于完整原文基线

Preference Track v0 每个 case 只有少量写入，`naive_markdown` 尚未面对真实长历史中的 context、噪声、延迟和成本压力。未来必须单独增加长历史偏好检索任务，才能评估抽取型记忆的规模化价值。

## 19. 实施前验收清单

开始正式编码和运行前，设计需满足：

- [ ] 正式系统只有 `naive_markdown`、`AMH`、`mem0`；
- [ ] `pure_vector` 和 `no_memory` 不进入正式跑分；
- [ ] 无历史输入仅用于 case 质量检查；
- [ ] 单项为 3 类 × 10 个，共 30 个；
- [ ] 综合为 15 组反事实双胞胎，共 30 个 case；
- [ ] 每个 writer Agent 只看到自己的局部对话；
- [ ] decision Agent 看不到历史原文和 ground truth；
- [ ] 每个 case 有结构化偏好事件、有效状态和唯一正确选项；
- [ ] 每个候选都有真实 trade-off；
- [ ] Agent D 输出固定 JSON；
- [ ] 完整保存 retrieved context；
- [ ] 每个 case 使用独立 memory store；
- [ ] reset、解析或系统错误不能静默忽略；
- [ ] reader temperature 设为 0；
- [ ] 先通过 12 个 smoke case，再扩到 60 个；
- [ ] 结果按分项能力展示，不制造一个掩盖差异的总分。

## 20. 一句话对外说明

> Preference Track v0 通过 30 个单项诊断 case 和 15 组反事实综合情境，测试不同 Agent 分别获得的用户偏好能否通过共享 memory 被新的 Agent 正确合并、更新、按场景使用，并避免传播过期或一次性偏好；正式比较 `naive_markdown`、`AMH` 和 `mem0`，以程序化 ground truth 评价最终决策、偏好使用正确性和运行效率。
